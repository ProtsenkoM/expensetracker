## Архитектура

- Подключить `@nestjs/cqrs`. Межмодульное взаимодействие выполнять через `CommandBus` и `QueryBus`, без прямых вызовов сервисов другого модуля.
- `UsersModule` содержит `UsersRepository`, `UsersService` и обработчики команд/запросов. Только репозиторий обращается к Prisma; сервис реализует работу с пользователями и паролями.
- `AuthModule` содержит контроллер, `AuthService`, JWT guard и обработчики авторизации. Репозиторий и сервис пользователей не экспортировать.
- Использовать синхронный CQRS внутри приложения. Event sourcing, брокер сообщений и события для регистрации в этот этап не включать.

## Команды и запросы

- `RegisterCommand { name, email, password }`: обработчик в `AuthModule` отправляет `CreateUserCommand`, затем выпускает JWT.
- `LoginCommand { email, password }`: обработчик в `AuthModule` выполняет `VerifyUserCredentialsQuery`, затем выпускает JWT.
- `CreateUserCommand { name, email, password }`: обработчик в `UsersModule` создаёт пользователя через `UsersService` и возвращает публичные данные.
- `VerifyUserCredentialsQuery { email, password }`: обработчик в `UsersModule` проверяет пароль и возвращает публичные данные пользователя либо `null`. Данные запроса и пароль не логировать.
- `GetUserByIdQuery { id }`: обработчик в `UsersModule` возвращает публичные данные либо `null`; используется JWT guard.
- Общий результат `PublicUser`: `id`, `name`, `email`, `createdAt`, `updatedAt`. Хеш пароля не пересекает границу модуля пользователей.
- Контракты команд, запросов и результатов хранить отдельно от реализаций обработчиков. Направление зависимости: `AuthModule` использует контракты `UsersModule`, обратной зависимости нет.

## Модель и API

- Prisma-модель `User`: UUID `id`, `name`, уникальный `email`, `passwordHash`, `createdAt`, `updatedAt`. Добавить миграцию.
- Email нормализовать через trim и lowercase. Пароли хранить в виде Argon2id-хеша; исходный пароль не сохранять и не нормализовать.
- `POST /api/auth/register` принимает `{ name, email, password }`, возвращает `201`; занятый email, включая конкурентную регистрацию, — `409`.
- `POST /api/auth/login` принимает `{ email, password }`, возвращает `200`; неверные учётные данные — одинаковый `401`.
- Оба endpoint возвращают `{ user, accessToken, tokenType: "Bearer", expiresIn: 900 }`. Методы `AuthService.register()` и `AuthService.login()` отправляют соответствующие команды.
- `GET /api/auth/me` возвращает текущего пользователя, полученного guard через `GetUserByIdQuery`.

## Защита и конфигурация

- Использовать `@nestjs/jwt`: HS256, claims `sub`, `iat`, `exp`, срок действия 15 минут.
- Глобальный guard проверяет подпись, срок действия JWT и существование пользователя. Некорректный токен или отсутствующий пользователь — `401`.
- Register, login и существующие health endpoints обозначить `@Public()`. Добавить `@CurrentUser()`.
- Обязательный `JWT_SECRET` — минимум 32 байта, без значения по умолчанию. Обновить `.env.example` и инструкции запуска.
- Глобальная валидация DTO: корректный email, имя после trim — 1–100 символов, пароль — 8–128 символов; неизвестные поля отклонять.
